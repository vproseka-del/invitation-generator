---

# 1. Purpose

This document defines how OpenCode should work on the InvitationGenerator project.

Its goal is to ensure consistent, understandable and scalable development.

---

# 2. Read Before Every Session

Before starting work, always review:

1. PROJECT_BRIEF.md
2. PROJECT_RULES.md
3. TODO.md

If additional context is required, consult the supporting project documentation before making assumptions.

---

# 3. Understand Before Coding

Before implementing any feature:

- understand why it is needed;
- understand what problem it solves;
- understand the expected result.

If the objective is unclear, ask for clarification before writing code.

---

# 4. Work in Small Steps

Never attempt to build the entire application in one step.

Break work into small, testable milestones.

After each milestone:

- explain what was done;
- verify it works;
- wait for confirmation before continuing.

---

# 5. Explain Decisions

Before making significant changes:

- explain the purpose;
- explain the proposed solution;
- explain why it is preferable.

Use language understandable to a non-programmer.

---

# 6. Prefer Simplicity

When several technical solutions exist:

1. choose the simplest;
2. choose the most reliable;
3. choose the easiest to maintain.

Only increase complexity when justified.

---

# 7. Architecture First

Every implementation must support future expansion.

Avoid decisions that make later development difficult.

---

# 8. Code Changes

Prefer small, logically complete commits.

Avoid modifying many files simultaneously without approval.

Ensure the project remains runnable after each change.

---

# 9. User Interface

The interface must remain:

- simple;
- clean;
- practical.

Visual effects must never reduce usability.

---

# 10. Generated Text

Generated letters must be:

- respectful;
- grammatically correct;
- natural;
- professional;
- persuasive without manipulation.

Avoid bureaucratic language and generic AI wording.

---

# 11. Error Handling

When an error occurs:

1. explain what happened;
2. explain why it happened;
3. propose the simplest solution.

Do not jump directly to implementation.

---

# 12. Suggestions

If you identify a better solution:

- describe it;
- explain advantages;
- explain possible disadvantages;

Do not change the project architecture without approval.

---

# 13. Development Priority

Always prefer:

- clear architecture over rapid coding;
- practical usefulness over unnecessary functionality;
- maintainability over short-term convenience.

---

# 14. Core Principle

Every decision should answer three questions:

- Does this make the system simpler?
- Does this make the system more useful?
- Will this still be a good decision one year from now?

If not, propose a better alternative.
